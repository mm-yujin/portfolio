컨텐츠 개발 · 미니보스 AI 로직 및 패턴

  • 각각 4~5종 이상의 패턴을 가진 미니보스 AI 로직과 전투 패턴을 개발했습니다 (패턴/스킬 총 15종 이상). 아래는 데모 페이지에 공개된 내용만 기재한 것입니다.
  • 플레이어를 따라오는 회오리 — 일정 시간 발사 방향으로 직진하다가, 타겟을 향해 프레임당 회전 각도를 제한하며 추적합니다. 그 결과 즉각 꺾이지 않고 크게 돌아 쫓아오는 움직임이 나옵니다.
  • 경고 후 돌진 — 플레이어와 일정 거리 이상 멀어지면 경고 장판을 깔고, 그 방향으로 강하게 돌진하며 데미지를 입힙니다.
  • 끌어당기는 장판 — 장판 영역 안에 플레이어가 있는 동안, 장판의 중심(몬스터 자신)을 향하는 벡터를 플레이어 이동 벡터에 더합니다. 조작권을 뺏지 않으면서 자연스럽게 중심부로 끌려가는 효과를 만듭니다.

로직 설계 · UI Manager 구조 설계 및 개발

  • 모든 UI의 최상위 클래스(UIBase)를 설계하고 특성별로 다섯 가지로 세분화해 상속 구조를 잡았으며, UI의 생명주기(생성/삭제)는 오직 UIManager를 통해서만 관리되도록 싱글톤 기반 중앙 제어 시스템을 구축했습니다.
  • UI 리빌드(Rebuild) 비용을 최소화하기 위해 역할별로 독립된 Canvas 구조를 설계했습니다. 하나의 거대한 Canvas가 통째로 더티되는 상황을 없앴습니다.
  • 상호작용이 필요한 UI 계층에 Stack 구조의 관리 로직을 도입해, 최상위에 떠 있는 UI만 입력을 받고 그 외 입력은 자동으로 차단되도록 했습니다. "팝업 뒤가 눌리는" 류의 버그가 구조적으로 사라졌습니다.
  • UI 특성에 따라 3가지 풀링 설정을 적용하고, Custom Attribute를 인터페이스화해 개별 UI 클래스에서 풀링 방식을 직접 지정할 수 있게 개발했습니다.

최적화 · 아이템 생성 및 습득 로직

증상
게임 플레이 중 첫 번째 아이템이 생성될 때 수백 ms 단위의 로딩 렉이 발생했고, 재화를 습득하는 과정에서 CPU 점유율이 폭증해 화면이 멈추는 현상(Spike)이 확인되었습니다.
원인
최초 생성 시 : 프리팹 읽기와 파일 헤더 로드가 메인 스레드에서 발생해 253.69ms의 지연. 재화 습득 시 : 반복문 안에서 재화 수만큼 습득 로직이 반복되고 원본 데이터를 LoadAll로 호출해, 아이템 개수만큼 Load와 Instantiate가 반복되며 83ms의 지연.
조치
런타임 중 프리팹 로드 부하를 없애기 위해, 씬 로딩 시점에 주요 아이템 모델을 미리 Instantiate 후 즉시 Destroy하는 Warm-Up 로직을 구현했습니다. 아이템의 SO 원본 데이터는 로딩 시점에 미리 로드해 캐싱하여 런타임 중 LoadAll 호출 케이스를 해소했고, 동일 아이템은 증가 수치를 합산해 단 1회의 인스턴스화와 트리거 체크만 수행하도록 수정했습니다.
결과
최초 생성 253.69ms → 84.08ms (약 67% 향상), 동일 수량 재화 습득 83ms → 31ms (약 62% 향상).

최적화 · 몬스터 AI 구조 개선 (BT → FSM)

  • 기존 레거시인 BT 방식이, 프로젝트 내 주요 몬스터 패턴(단일 상태 / 순차적 전이)에 비해 과도한 탐색 비용을 소모한다고 판단했습니다.
  • 몬스터 개체 수가 증가할 경우의 성능 안정성을 선제적으로 확보하기 위해 구조 개선에 착수했고, 복잡한 의사결정 분기보다 상태 전이가 명확한 프로젝트 특성에 맞춰 FSM 기반으로 AI 구조를 재설계했습니다. 다중 조건(Any/All)과 Invert를 적절히 혼합해 논리 구조를 정리했습니다.
  • 레거시 코드를 유지하는 것만 고집하기보다 콘텐츠의 성격에 맞는 적정 기술을 선택하는 쪽이 맞다고 봤습니다.
  • NodeCanvas를 활용해 시각적으로 명확한 상태 전이도를 구축했고, 기획·디렉터 측에서 파악이 용이해져 협업 효율이 올라갔습니다.

최적화 · 런타임 메모리 누수 해결

증상
맵 진입 후 10분당 약 0.89GB의 급격한 메모리 누수를 확인했고, 단 10분 만에 런타임 머테리얼 개수가 30만 개를 돌파하는 비정상적 수치를 기록했습니다.
원인
Unity Memory Profiler로 스냅샷 비교 분석을 수행한 결과, 특정 외부 셰이더 에셋 내부에서 동일한 이름의 머테리얼이 초당 몇 백 개씩 생성되고 있었습니다.
조치
분석된 프로파일러 데이터와 재현 경로를 정리해 팀 내에 공유했고, 결함이 있는 외부 라이브러리의 교체(마이그레이션) 필요성을 피력하며 가이드라인을 제시했습니다.
결과
팀 내 재확인을 거쳐 에셋 업데이트 등의 방법으로 문제를 해소했고, 30분 이상 연속 플레이 시에도 머테리얼 개수를 1,000개 미만으로 안정적으로 유지하게 되었습니다.

툴 제작 · 애니메이션 프리뷰 툴

  • EditorApplication.update를 활용해, 런타임 진입 없이도 에디터 모드에서 애니메이션과 공격 로직을 시뮬레이션할 수 있는 독립적 루프 시스템을 만들고 그 위에 프리뷰 툴을 제작했습니다.
  • 무기별로 오버라이드된 애니메이션 클립을 에디터 상에서 정확히 바인딩해 재생하도록 구현했습니다.
  • 애니메이션 이벤트의 설정 위치를 함께 표시해, 캐릭터가 이동하는 시점과 히트박스가 생성되는 시점의 타이밍을 명확히 드러냈습니다.
  • 캐릭터의 이동 예상 경로와 무기별 히트박스를 씬 뷰에 실시간으로 그려내어 데이터를 직관적으로 확인할 수 있게 했습니다.
  • 에디터 윈도우 내에서 공격 거리 및 이동 커브를 수정하면 즉시 프리뷰에 반영되는 동시에 원본 프리팹에도 저장되도록 하여, 밸런싱 작업의 반복 주기를 크게 줄였습니다.

자동화 · Lighting 설정 자동화 및 에셋 관리 시스템

  • Unity Lighting Setting의 Environment 정보(Skybox, Fog 등)가 라이팅 데이터 베이크 시 별도로 저장되지 않아, 씬 전환 시 설정이 유실되는 문제를 발견했습니다.
  • ScriptableObject를 활용해 환경 설정 데이터를 별도로 저장하되, 씬 저장 시 해당 데이터를 자동 추출해 에셋으로 생성하도록 구현했습니다. 별도의 저장 절차가 필요 없습니다.
  • 에셋 경로 자동 매칭 로직을 적용하고, 에디터 이벤트(씬 로드 이벤트)를 활용해 해당 시점에 경로 내 존재하는 환경 데이터를 즉시 적용하는 자동 적용 시스템도 구축했습니다.
  • 기존 데이터가 있는데 데이터가 변경될 경우 확인 팝업을 띄워, 의도하지 않은 덮어쓰기를 방지했습니다.
  • 결과적으로 멀티 씬 작업 환경에서의 라이팅 설정 유실 문제를 근본적으로 해결하고, 수동 설정 과정을 생략해 아트 직군의 편의성을 크게 높였습니다.

증상
천문대 시스템의 '추천 연구' 팝업에서, 현재 건물 레벨로 즉시 연구 가능한 항목이 있음에도 건물 업그레이드가 필요한 연구가 우선 추천되는 현상이 있었습니다. 이때 추천된 연구를 클릭해 진입하면 안내된 정보와 실제 연구 단계가 일치하지 않는 문제도 함께 발생했습니다.
원인
추천 알고리즘 내에 '현재 건물 레벨로 즉시 업그레이드 가능한지'에 대한 조건이 누락되어 있었습니다. 또한 추천 대상을 탐색할 때 무조건 '현재 완료된 연구 레벨'만을 기준으로 데이터를 가져오고 있어, 상황에 따라 '다음 단계 연구(현재 레벨 + 1)'의 요구 조건을 정확히 판별하지 못했습니다.
조치
LINQ의 OrderBy를 활용해 현재 건물 레벨이 해금 조건을 충족하는 항목을 0순위로 배치하도록 정렬을 보정했습니다. 또한 추천 리스트 생성 시 이번 레벨 연구를 다 끝낸 경우와 아닌 경우를 나누어, 현재 연구 레벨 또는 현재 레벨 + 1단계의 테이블을 각각 참조하도록 로직을 보강했습니다.
결과
기획 사양에 부합하도록 추천 시스템을 정상화하고, 연구 아이콘 및 이름 정보가 실제 데이터와 일치하도록 무결성을 확보했습니다.

결과
채팅 수신 및 읽음 상태의 동기화 오류를 해소하고, 미확인 메시지 알림의 신뢰도를 제고했습니다.

LoadType을 Streaming으로 변경했습니다. BGM의 경우 Unity 공식 문서에서도 Streaming을 권장합니다.
결과
동일한 파일 기준 사용 시 0.17MB, 미사용 시 0.006MB로 최소 50배의 메모리 점유율 감소(BGM당 약 10MB 절약). 플레이 중 BGM이 약 5번 바뀐다고 가정하면 약 50MB를 절약할 수 있습니다.

개발도구 개선 · 번들 제작 툴

  • 기존에는 에셋 번들을 한 개 단위로 각각 생성한 뒤, 작업자가 '에셋 번들 리스트' txt를 직접 작성해야 했습니다 — 버전 번호를 직전 대비 +1 올리고, 작성일자를 금일로 수정하고, 제작된 번들 용량을 확인해 직접 기재하고, 이전 버전 내용은 ;를 붙여 주석 처리하는 과정이었습니다.
  • 이를 체크박스 다중 선택 + 일괄 생성으로 바꾸고, 리스트가 스스로 작성되도록 했습니다. 버전은 직전 대비 자동 +1, 작성일자는 DateTime, 용량은 FileInfo를 활용한 MB 단위 표기, 이전 버전은 자동 주석 처리되며, 직후 리스트 번들까지 자동 생성됩니다.
  • 에셋 번들 업데이트 과정에 소요되는 시간이 약 62% 감소(번들 15종 기준 평균 40분 → 15분)했습니다.
  • 텍스트 데이터 번들의 경우 암호화 프로그램 팝업 및 실행과 2차 에셋 번들 생성 과정을 자동화했습니다. 작업 절차 4단계 → 2단계, 소요 시간 평균 7~8분 → 3~4분으로 단축했습니다.
