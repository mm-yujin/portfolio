The Pink Robot Action roguelite · PC (Steam)

Sep 2025 – Mar 2026
Studio Take Five Studios Stack C#, Unity, UGUI Team 3 client programmers Role Prototype & demo development Steam page ↗

Skill chain & memento system

  • Designed and built the core build-crafting mechanic: basic attacks and skills act as triggers that cascade through linked memento effects, so a single hit can fire a chain.
  • Each memento carries a randomized node direction (1–4 sides) and rarity, turning a limited board into a spatial optimization puzzle. Dozens of memento types produce genuinely different runs.
  • Effect values scale with the action state the chain fired from — Normal / Charging / Perfect — so execution skill converts directly into character power.
  • Built the inventory ↔ board UX: free re-slotting outside combat, colour changes on node connection, and tooltip-driven detail so a dense system stays readable at a glance.

Mini-boss AI & combat patterns

  • Authored mini-boss AI with 4–5 patterns each, 15+ patterns and skills total. Three that are visible in the public demo:
  • Homing tornado — travels straight for a fixed window, then tracks the player with a per-frame turn-rate cap, so it arcs wide and comes back around instead of snapping onto you.
  • Telegraphed charge — when the player breaks a distance threshold, the boss lays a warning decal and then dashes hard along it.
  • Pull field — while the player stands inside the zone, a vector toward the field's centre (the boss itself) is added to player movement, dragging them in without ever taking control away.

UI framework architecture

  • Designed a UIBase root type specialized into five categories by behaviour, with lifecycle owned exclusively by a single UIManager — nothing creates or destroys UI on its own.
  • Split canvases by role to keep rebuild cost local instead of dirtying one giant canvas.
  • Stack-based input layering: only the topmost interactive UI receives input; everything below it is blocked automatically, which removed a whole class of "clicked through the popup" bugs.
  • Three pooling strategies, selectable per UI class through a custom attribute exposed as an interface, so each screen opts into the right cost model.

Optimization · item spawn & pickup

Symptom
A several-hundred-millisecond hitch the first time an item spawned in a run, plus a CPU spike that froze the screen whenever the player picked up currency.
Diagnosis
First spawn: prefab read and file-header load happening on the main thread — 253.69ms. Pickup: the loop called LoadAll on the source data once per unit of currency, so Load + Instantiate ran N times — 83ms.
Fix
Added a warm-up pass that instantiates and immediately destroys key item models at scene load; pre-loaded and cached the ScriptableObject source data so LoadAll never runs at runtime; aggregated identical items so pickup does one instantiation and one trigger check regardless of quantity.
Result
253.69ms → 84.08ms (−67%) on first spawn, 83ms → 31ms (−62%) on pickup.

Optimization · monster AI, behaviour tree → FSM

  • The legacy behaviour-tree setup was paying full traversal cost for monsters whose real behaviour was single-state or a simple sequential transition.
  • Rebuilt AI on an FSM to get ahead of the cost curve before monster counts grew, mixing Any/All conditions with Invert to keep the logic compact.
  • The point wasn't "FSM is better" — it was picking the technology that matched the content, rather than defending legacy code.
  • Built the graphs in NodeCanvas so designers and the director could read the state transitions visually and reason about behaviour without asking a programmer.

Optimization · runtime memory leak

Symptom
~0.89GB of memory lost every 10 minutes after entering a map, with the runtime material count passing 300,000 in that same window.
Diagnosis
Snapshot diffing in the Unity Memory Profiler showed a specific third-party shader asset creating hundreds of identically named materials per second from inside its own code.
Fix
Wrote up the profiler data and a reproduction path, shared it with the team, and made the case for migrating off the faulty library — including a guideline for the replacement.
Result
After the team's own verification and an asset update, material count now stays under 1,000 across 30+ minutes of continuous play.

Tooling · animation preview window

  • Built an editor-mode simulation loop on EditorApplication.update, so animations and attack logic can be previewed without entering play mode at all.
  • Binds per-weapon override clips correctly in editor and plays them back accurately.
  • Surfaces animation event positions on the timeline — exactly when the character moves and when a hitbox spawns — instead of leaving those as invisible data.
  • Draws the character's predicted movement path and per-weapon hitboxes live in the scene view.
  • Editing attack range or motion curves in the window updates the preview instantly and writes back to the source prefab, which collapsed the balancing loop for designers.

Automation · lighting environment persistence

  • Found that Unity's Lighting Environment settings (skybox, fog, etc.) aren't stored alongside baked lighting data, so they were silently lost on scene transitions in our multi-scene setup.
  • Moved that state into a ScriptableObject that is auto-extracted on scene save — no extra step for anyone, the asset just appears.
  • Added automatic asset-path matching plus a scene-load hook that applies the matching environment data at the right moment, so lighting is correct without manual setup.
  • A confirmation popup guards against unintentionally overwriting existing data.
  • Removed a recurring source of "the lighting broke again" from the artists' day entirely.

Automation · localization via Google Sheets

  • Manual entry into the Localization table stopped scaling once the project passed 10+ languages.
  • Wired up the Localization package's Google Sheets integration to move translation into a shared cloud sheet.
  • Chose editor-time sync over runtime sync deliberately — no credentials shipped in the build, no runtime cost, no network dependency in game.
  • Split Push/Pull into granular operations so two people editing at once don't clobber each other.
  • Wrote and distributed the update guideline and manual, so designers could own their own strings.

  • Integrated 23 new timeline sequences, a speech-bubble dialogue system that runs during cutscenes, and a screen-border effect during invasions.
  • Built the interface for repairing and constructing buildings by touching them mid-cinematic.
  • Added per-state management (destroyed / repairing / complete) for pre-placed buildings, driving which model is shown by progress.
  • Wrote the migration that force-clears guides for existing players based on their actual progress.

Feature · town build queue

  • Promoted build-slot information from a buried menu to the top bar of the main screen.
  • State-driven UI on LOCK / IDLE / WORKING — lock icon, add button, or building icon plus progress gauge.
  • Live monitoring of construction progress, remaining time and building name, with separate expiry tracking for time-limited slots.
  • Hooked packet responses (speed-up item used, construction complete) to refresh the UI immediately rather than on the next poll.

Feature · speech bubbles during timelines

  • Built a custom signal system with paired start/end emitters that define a dialogue window inside a Timeline.
  • Drop multiple StringKeys into one window and the system auto-splits the duration so lines play out in sequence — no manual per-line timing.
  • Positioned bubbles from Renderer.bounds with billboarding, so they survive character movement and camera rotation.
  • Wrote a manager that scans and caches every marker in the track on start, so nobody has to hand-place signal receivers in each scene.
  • Net effect: detailed dialogue staging became a pure editing task.

QoL · one-tap medal box opening

  • Growth materials ("medals" and "essences") were often sitting inside unopened boxes, forcing a round trip out to the inventory to use them.
  • Extended the "Go" button shown on insufficient currency to live-check whether the inventory holds a selection box containing that exact material.
  • If it does, the button routes to a dedicated popup instead of the inventory — the player never leaves the growth screen.
  • Gated the whole feature behind a server-side flag as a kill switch, so live issues could be rolled back to the old path instantly.
  • Three steps down to one, shipped safely into a live game.

QoL · continuous summon

  • The [summon → cutscene → result → summon again] loop was pure fatigue for players holding a lot of currency.
  • An Auto Summon toggle repeats the summon logic uninterrupted up to the currency the player actually has.
  • Handled the failure cases properly — running out of currency mid-loop or filling the inventory exits the loop safely and shows the result screen rather than stalling.

Bug · observatory research recommendation

Symptom
The "recommended research" popup suggested research that required a building upgrade first, even when something was immediately available. Clicking through showed information that didn't match the actual research tier.
Diagnosis
The selection algorithm had no condition for "can this be started at the current building level", and always pulled data from the completed research level — so it could never evaluate the requirements of the next tier (level + 1).
Fix
Reordered with a LINQ OrderBy that places entries whose unlock conditions the current building level satisfies at priority 0, and branched the table lookup between the current level and level + 1 depending on whether the current tier was exhausted.
Result
Recommendations match the design spec, and research icons and names are consistent with the underlying data.

Bug · unread chat message count

Symptom
Correct with a single chat room, but with several open, one room's badge would stop updating — and messages arriving after the player had left a room were being marked as read.
Diagnosis
The "current room ID" variable was never cleared on exit and only refreshed on entering a new room. Combined with the "don't count messages from the room you're in" rule, that meant the room you just left kept swallowing its own notifications.
Fix
Reset the variable at the moment of leaving, and pushed the state change to the server immediately to close the client/server latency window that could reintroduce the same class of bug.
Result
Read-state sync fixed, and unread badges became trustworthy again.

Optimization · graphics-quality-driven NPC population

  • Ambient NPCs wandering the town carried a measurable render and memory cost, so I tied their population to the graphics quality setting.
  • Dropping to Low despawns the existing NPCs (10–20 on average) and blocks further spawns; going back to High respawns them and resumes their animation.
  • Result: batches −14.4% (160 → 137), draw calls −14.0% (164 → 141), and total used memory −3.6% (3.61GB → 3.48GB).

  • Buff application on equip, a hide-equipped-title setting, and title swapping driven by preset changes.

  • Contextual suppression rules — titles hide while using a stealth skill or when fighting as a mercenary in a world siege.
  • Acquisition and expiry notifications, plus red-dot badging on the menu icon.

QoL · warehouse auto-store, bulk relist, bulk retrieve

  • Auto-store: LINQ-split consumable and misc items whose index matches between inventory and warehouse, verify per-slot stack limits and whether the warehouse actually has room, then send the store request.
  • Bulk relist: filter the sell list down to expired listings, re-fetch the original price and fee from the server, and re-register every one of them at the same price.
  • Bulk retrieve: request retrieval for the batch, and clear each entry from the list as its inventory-create packet comes back.

Crash · stacked stat-up effects

Symptom
Intermittent hard crashes during early-game combat.
Diagnosis
Effects fired on level-up and on every stat increase (strength / agility / vitality / proficiency) had no cap. At low levels a single fight raises dozens of stats, so effects were instantiated in a burst — a ~1.3GB memory spike in the profiler.
Fix
Observed that past three overlapping effects, shader blending makes the count visually indistinguishable — so I counted active effects on play start, released on end, and skipped the call past three. Also replaced Instantiate() with a pool to remove the create/destroy cost.
Result
Spike stabilized from ~1.3GB to roughly 20MB, and the crash stopped reproducing even on small-memory devices (iPhone 13 mini, iPad mini 3).

Optimization · audio clip load type

Symptom
BGM clips were authored with load type Compressed In Memory.
Diagnosis
A 2.3MB clip occupied 12.6MB of actual memory, and every map transition that changed the BGM loaded another ~10MB on top.
Fix
Switched to Streaming — which is also what Unity's own documentation recommends for background music.
Result
Same file now costs 0.17MB while playing and 0.006MB when idle — at least a 50× reduction, ~10MB saved per BGM, roughly 50MB across a session with five music changes.

Tooling · asset bundle build pipeline

  • The old flow built bundles one type at a time, then required someone to hand-write the bundle list text file: bump the version, type today's date, check each bundle's size in MB, and comment out the previous block with ;.
  • Rebuilt it as checkbox multi-select with batch generation, and made the list write itself — version auto-incremented, date from DateTime, sizes from FileInfo in MB, previous entries auto-commented, and the list bundle generated right after.
  • ~62% faster: 40 minutes down to 15 for a typical 15-bundle release.
  • Separately, automated the text-data bundle path — launching the encryption program, entering the password, and running the second-pass bundle build all happen behind one popup. Four manual steps → two; 7–8 minutes → 3–4.

Japan launch

  • Age-based spending cap: age packet on shop entry, an age confirmation popup when the server has no record, pushing the new value to the server and mirroring it into PlayerPrefs for cross-device checks — with the purchase flow gated on the server's verdict before it can proceed.
  • I2 Localization for in-game UI and script translation.
  • Build and submission management: Google Play APK/AAB, and Apple App Store via Unity → Xcode → TestFlight.
  • Firebase Cloud Messaging for push notifications.
  • Adjust: token issuance, event registration, and the in-script event-send code via the Adjust SDK.
  • QA support for the Japanese build.
